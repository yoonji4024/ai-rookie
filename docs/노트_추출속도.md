# 음향 피처 추출 속도

## 왜 쟀나

"음성에서 피처 뽑는 게 느리지 않냐"는 지적. KPI가 분류 지연 5초 이내라 실측이 필요했음.

측정 도구: `src/agents/analysis/features/profile_speed.py`
대상: 60초 음성 (16kHz 모노 wav), 맥북 에어

## 결과

| | 개선 전 | 개선 후 |
|---|---|---|
| 합계 | 4.49초 | **1.74초** |
| 실시간 대비 | 0.07배 | 0.03배 |
| KPI(5초) | 아슬아슬 | 여유 |

61% 단축.

## 병목이 praat이 아니었다

처음엔 praat 계산(HNR·jitter·shimmer·CPP)이 느릴 거라 봤는데 아니었음.

**개선 전 항목별**

| 항목 | 시간 | 비중 |
|---|---|---|
| 오디오 로드 | 2.94초 | 65% |
| CPP | 1.06초 | 24% |
| HNR | 0.23초 | 5% |
| PointProcess | 0.09초 | 2% |
| pitch(F0) | 0.07초 | 2% |
| MFCC | 0.07초 | 2% |
| jitter, shimmer | 0.00초 | — |

praat 전체를 합쳐도 1.4초. **로드 하나가 그보다 두 배 이상 먹고 있었음.**

## 원인과 수정

`librosa.load(path, sr=16000)`는 파일이 **이미 16kHz여도** 디코딩·리샘플 경로를 탐.

→ 이미 목표 샘플레이트인 wav는 `soundfile.read`로 직접 읽고, 아니면 librosa로 폴백.
   (`extract_acoustic._load_audio`)

**2.94초 → 0.01초**

## JIT 컴파일 비용 주의

로드를 고치자 MFCC가 0.07초 → 4.84초로 튀는 현상.

계산이 아니라 librosa(numba)의 **첫 호출 컴파일 비용**. 이전엔 `librosa.load`가 먼저 돌며
그 비용을 흡수하고 있었을 뿐. 로더를 바꾸니 MFCC가 뒤집어씀.

- 프로세스당 1회만 발생 (약 2.1초)
- 서버는 계속 떠 있으므로 **기동 시 미리 태움** (`server.py` startup 이벤트)
  → 안 하면 하필 첫 사용자 요청만 느려짐
- 측정도 워밍업 후 해야 정상 상태 성능이 나옴 (`profile_speed.py` 기본 동작)

## 더 줄여야 한다면

분석 구간을 30초로 제한하면 **0.78초**까지 감소(83% 단축). CPP는 이미 60초 캡 적용 중.
현재 여유가 충분해 적용하지 않음. 평균값 기반 지표라 구간을 줄여도 값은 안정적.

## 부수 효과

대량 실험에도 동일하게 적용됨. DementiaBank 1,035개 추출이 수십 분 걸렸던 것도
같은 로드 병목이 원인. 재실험 속도가 크게 개선됨.
